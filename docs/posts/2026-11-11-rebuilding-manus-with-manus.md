Manus 联合创始人 Tao Zhang 在 10 月 30 日写了一篇内部实验报告：工程、产品、市场怎么默认和 agent 并肩干活，以及哪些地方已经摔过。值得记下的不是「一人同时开十几路会话」，而是三件事：半接入旧流程只会变成噪音；agent 缺的是整幅图，不是更好的提示词；能自己跑的，必须有可检查的终点，其余一律人拍板。

## 半接入等于加噪音

他们 2026 年以前也做过常见动作：客服用 AI 摘要、工程师用编码助手、频道里丢分析 bot。每块单独有用，但环路没接上，还是原来那套工作方式，只是多了一堆 AI 互相说话。

他们常提一句：software engineering is programming integrated over time。写代码好量化；把复杂产品养几年、还不塌，才是真正的测试。Manus 已经上线一年多，问题变成：换工作方式之后，产品还能否持续改进，同时每人多干一些。目前他们的答案是可以，但前提是环路真的闭合。

## Mono 不是并仓，是给 agent 的入口和手册

跨栈改代码最大的摩擦在交接：前后端各自理解需求，对完接口再花几天修错位。如果 agent 能跨栈写，一个人能不能从头跟到发布？拦路的是上下文——代码散在多个仓库，没有一个 agent 能一次看全系统。

他们没把仓库合成 monorepo，而是做了内部入口 Manus-mono（简称 Mono）：一份写给 agent 的手册（每个仓做什么、怎么拼在一起、怎么协作），外加架构决策记录库。新会话先读前人为什么这样决定，再按需把仓库拉进来。并行开发用 Git worktrees。

Mono 是一步步长出来的，每一步都在修上一层暴露的瓶颈：

1. 先看到整系统：补单仓里没有的业务上下文。
2. 本地验证：推测试环境原来要 5 到 10 分钟；现在整套 Manus 能在笔记本上跑，检查变成秒级。
3. 带范围地查生产：给日志、配置、报错的有限权限，用来定位线上问题。
4. 把发布跑通，但审批仍在有发布权的人手里。
5. 端到端验收变成慢点之后，Mono 开始用测试账号，在浏览器和手机模拟器里跑真实用户路径。

所以 Mono 不只是代码 wiki。测试怎么跑、怎么发版、什么能碰什么不能碰，都在同一套共享知识里。运维把发布流程写进去之后，人和 agent 都能跑发布，闸门还在人这边。

## 三条 agent，人在中间做决定

另一半是让 agent 自己把问题找上门。用户报障不再先在支持、产品、分诊之间传一圈：内部 agent 先调查、追到引入问题的那次改动，再在 Slack 里标出责任工程师。工程师决定要不要修，再交给自己的 agent。第三个 agent 跑相关测试和路径做核对。

分工写得很硬：分诊那个不能改代码，只能调查和汇报；改动来自工程师自己的 agent，而且是在人点头之后；没有发布权的人签字，什么都不上线。

信任也不是靠「模型已经够强」。他们以前主分支必须两位资深工程师之一签字，agent 产量上去之后，人审成了队列。后来补了两块：agent 进它被拉进的 Slack 线程，有人说「Go」时已经带着讨论结论；改完能在真实流程和回归测试里跑一遍。再加一层用最强模型的 review bot，支付等敏感路径另加规则。Bot 替换的是排队，不是合并权——agent 可以开 PR，不能在没人明确同意时合进 main。

## 没有可检查的终点，就不要放全自动环

他们试过完全自主的环：agent 从内部反馈里捞条目、逐个开项目，有人让它跑了一个周末。周一早上，两百多条等他拍板。

教训很直接。测试能过能不过、页面能开能开不了，这种才适合让 agent 自己跑。值不值得做、产品做没做对，没有这种检查，人必须决定。人做决定的速度也跟不上无刹车的环；没人决定该不该做，也就没人拥有结果。

工程变快之后，瓶颈滑到「该做什么」。有人让工程师当 builder，有人让 PM 改代码，都还卡在交接上。Mono 把规则带着走：动模型调用或成本，先要负责人点头再写代码；PM 的改动走和工程师同一套 review 和测试；还能用测试账号走注册和支付并录下每一步。人从「环里补刀」变成「环上设规则、盯关键节点、对结果负责」。文里问得很尖：如果这件事只要一秒、还零成本，你还发吗？有时答案是否。

## 可立刻落到自己仓的四点

1. 先闭合环路，再堆助手。调查、改代码、验证、发布如果互不相通，加再多 bot 也只是噪音。
2. 给 agent 一份跨仓手册和 ADR，而不是先并仓。本地要能秒级验证；发布和合并权留在人这边。
3. 分诊 / 调查的角色不要有写代码的权限。改动由负责人自己的 agent 做，核对另开一条，人做中间的判断。
4. 只把「成功可自动检查」的工作交给自主环。没有终点检查的事项，不要让它周末自己开两百个项目。
