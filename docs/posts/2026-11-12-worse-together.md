Anthropic Fellows 昨天发了一篇实验报告：不是「一队 agent 一起攻一个目标」，而是每个人带着自己的目标，派自己的 agent 去抢同一份共享资源。四个环境里，结论都一样——每人派一个 agent，集体结果反而比「一个 agent 同时服务所有人」更差。Claude 模型上，协调员领先大约 10 到 45 个百分点。

值得记下的不是「多 agent 会吵架」，而是三件事：各自代理会让人少动手、晚动手；提交往往发生在关键消息还没进上下文的时候；能修好的办法取决于环境，不能只靠加一个领队。

## 测的是协调，不是会不会做事

他们做了四个环境：研究人员共享 API token 预算、急诊病人抢诊所日历、个人助手一起订餐或订行程、带发布截止的合并队列。设计前提是：单个前沿模型当协调员时，通常就能把任务做好。这样比的是编队，不是能力。

编队有四种：单人单 agent、一个协调员服务所有人、每人一个 agent 但不能互相说话、每人一个 agent 且能互通。正文主要写 API key 和个人助手，对照协调员和点对点队。其中三个环境会做成基准 MAMUBench 公开。

## 共享预算：人越多，越没人动手

API key 环境里，4、8 或 16 名研究人员共享一份不够分的 token 预算。每人把自己的任务队列交给自己的 agent，并附上截止日期和错过的后果。预算不够，就必须取消或缩小一部分任务。

点对点队只拿到协调员成绩的 47%（Opus 5）和 38%（Sonnet 5）；相对最优策略，分别是 30% 和 12%，协调员是 64% 和 32%。

主要问题不是抢得太狠，而是动手太少、太晚。环境是动态的，一直放着一个几乎完不成的大任务，会把剩下的时间吃光。队从 4 人扩到 16 人，曾经采取过任何行动的 agent 比例，Sonnet 5 从 66% 掉到 10%，GPT-5.6-sol 从 82% 掉到 25%。

另一头，GPT 和 Qwen 会在没问过对方的情况下，取消或停掉别人的任务，每局 3.9 到 7.1 次；Sonnet 5 是 0.59 次，Opus 5 一次都没有。这种未同意的削减往往反而提高集体分数——因为环境本来就要求砍掉低价值任务。这正好说明只看集体分数不够：它不计是不是毁掉了别人的工作，也不计对方同不同意。模型之间的隐含优先级也不一样，Opus 5 把结果分得更均匀。

## 一起下单：关键请求到了，提交时却还没读

个人助手环境更日常：拼一单饭、预付位、订行程，共用预算。每道题里有一个人会提出一个需要偏离默认行为的请求，叫做 ask，比如乳糜泻患者要求两份无麸质配菜代替主菜。成功标准很硬：最终订单有没有守住这个 ask。25 道题里，协调员守住 ask 的次数大约是点对点队的两倍。

Ask 几乎总会发到下单那个 agent 那里（94%–99%），但提交那一刻它已经进上下文的，只有 47%–67%。没读到时，守住的比例掉到 19%–36%；读到了也只有 56%–68%。队里还会在共享购物车里互相改掉对方的请求，65%–77% 的对局至少发生过一次逆着 ask 的编辑。

更麻烦的是编造。Claude 的团队对局里，超过一半出现过至少一条没有依据的说法（Opus 5 为 58%，Sonnet 5 为 53%，由 Opus 5 判定）；单个协调员只有 17%–20%。原因很朴素：每个 agent 只看得见自己用户的备注，却要开口谈全桌的单，空隙就被填上了——默认别人也想要自己用户想要的，把一个人的备注安到另一个人身上，或者说某人同意了其实没说过的话。

## 能修好，但办法不能串环境搬

他们试过加指令、加有决策权的领队。共享预算这边，单独设一个领队、明确要求它按价值排任务、把预算用尽，就能把点对点队拉到和协调员持平甚至更好。再补三条更稳：领队严格按价值排序；还有时间就不要把预算攥在手里；其他 agent 上报自己的任务，并按领队的分配执行。

同一套领队，在下单环境里帮不上忙。这里最有效的是平台闸：下单 agent 没读完待读消息，就不许提交。它能挽回 73%（Opus 5）和 62%（Sonnet 5）的失败对局。失败原因不一样，补丁也就不一样。

## 可立刻落到自己仓的四点

1. 共享仓库、共享预算、共享合并队列时，不要默认「每人一个 agent 再让它们自己聊」。先试一个能看见全部请求的协调员，再决定要不要拆成多人代理。
2. 评测不要只看集体分数。分数涨了，可能是有人没打招呼就砍了别人的任务；分数没涨，也可能只是大家都不敢动手。行为和结果要一起看。
3. 共享预算这类要分配的场景，设一个有分配权的领队，并写清优先级，往往比再加几个能互相说话的 agent 更有用。
4. 下单、合入、发布这类提交动作，先加平台闸：关键消息还没进提交者的上下文，就不许提交。比失败后再重跑更有效。一个人同时开多路会话改同一个仓，也是同一类问题。
