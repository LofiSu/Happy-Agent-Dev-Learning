Manus 11 月 6 日发了一篇内部访谈：四人数据团队做了一个数据 agent，每周有 40 多人在用。文里几乎不谈模型怎么选，核心是三件事：数据怎么连、业务上下文怎么写、权限卡住时怎么接着干。

11 月 11 日那篇写的是给编码 agent 整幅图。这篇是同一思路落到数据上：把表接进来还不够，还要一张业务地图，告诉 agent 每个指标怎么定义、每张表能解答什么、表和指标之间怎么走。

## 先自动化自己的查询

他们没有一上来就给全公司做工具。先让数据团队自己不再手写查询，把日常分析改成跟 agent 对话。访谈里的说法是：你其实是在做一个自己的副本。

第一版大约一周就能跑起来。数据是分批接的：先接稳定的汇总指标，再接营销数据，再接更细的产品数据。一类连稳了，再接下一类。他们也明确说，不必等数据洗干净再开工，定义可以边用边收。

## 业务地图比连接更要紧

光有查数的工具，agent 还是不知道该去哪张表、该用哪套口径。数据团队单独做了一份知识库：指标怎么定义、每张表适合回答什么问题、表和指标怎么关联。

有了这张地图，没有现成看板的问题也能走完分析路径：选对表、用对定义、顺着指标往下追。对这个四人团队来说，以后真正要周更的不是 agent 本身，而是这份知识库。业务一变，就补新表和新定义；用的人不用跟着改，项目里更新一次，所有会话都能用到最新版。

他们回头看失败，多半也落在这两处：知识库缺了一条，或者某个定义写得含糊。所以要定期抽查真实问答，看 agent 是不是走对了路、给的判断靠不靠谱，再把漏洞补回去。

## 答案按使用的人来写

数据团队想看的是数怎么算出来的。业务同事想看的是这个数意味着什么。所以面向全公司时，他们要求每个答案盖住三件事：

- 这个变化大概说明什么
- 哪些发现已经稳到可以动手，并给出下一步
- 哪些还太弱，得找数据团队再核对

后一项很关键。agent 会查没人拉过的数，也会在看板之外追「为什么」。如果不把不确定的地方标出来，业务侧很容易把一次探查当成结论。

## 权限按主题拆，批完自动接着干

他们觉得最难的不是把 agent 跑起来，而是公司政策和护栏。不是所有人都能看所有表。做法是在表上做一层按主题拆开的治理，并把这些访问规则告诉 agent。

以前看不到某张看板，就要提工单等着。现在用户问到自己没有权限的表，agent 会在内部审批系统里发起申请，交给对应的数据负责人。批完之后，任务自动恢复，把答案补完。这和 11 月 14 日那篇里「需要人批准就结束这次 run，用事件把 session 接回去」是同一类结构：人只做决定，worker 不要空等。

工具也放到问题本来出现的地方。他们把数据 agent 放进 Slack，人在线程里追问、把答案转到频道，比再做一个单独入口更容易用起来。

## 可立刻落到自己仓的四点

1. 先自动化分析师自己的查询，再对其他团队开放。不要一上来就做全公司入口。
2. 接数据的同时写业务地图：指标定义、表能回答什么、表和指标怎么连。地图比连接更影响对错。
3. 面向业务的回答要同时给出含义、可执行的下一步，以及还需要人核对的部分。不要只丢一个数字。
4. 权限按主题拆开，并写进 agent 能读的规则。缺权限时发起审批，批完再恢复这次任务，不要让人重新问一遍。
