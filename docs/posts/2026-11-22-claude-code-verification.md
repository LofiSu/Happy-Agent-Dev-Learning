Addy Osmani 11 月 16 日在 claude.dev 写了一篇工程文，把 Claude Code 团队怎么让 agent 用证据验证自己的工作讲得更细。11 月 8 日那篇写的是分层 review：PR 前自证、按风险用人、自动审要收敛。这篇补的是验证这一层本身怎么搭——什么测试值得投、验证技能放哪、闸门怎么加，以及检查如何不被这次改动改掉。

他们的前提很直接。团队里大约九成代码由 Claude 写并审。没有验证循环，你同时只能盯一两台 Claude，因为每一步都得自己看。有了循环，才能并行跑几十、上百台。验证一旦写成可反复执行的测试、基准或规格，就可以少花 token、多跑几遍，失败结果还能收回去改 hook 或 `CLAUDE.md`。内部在结构化文件生成上做过对照：单独用一份评分标准再检查一轮，任务成功率最高能多大约 10 分，最难的题增益最大。

## 三种更值得投资的测试

不管选哪一类，有两个坑要先避开。测试若是 flaky，agent 会被训练成「再跑一遍」而不是修代码。测试若太慢，批量里跑的次数会变少，问题更难定位。更重的测试适合放在提交之前。

若只能先做一种，他们建议做 end-to-end。这类测试写的是真实用户路径，整条功能要么通、要么不通，完成条件和失败点都明确。单元测试更快、也更稳，但 agent 和测试都可能只看到任务的一部分，测过了功能照样坏。E2E 更难被糊弄。有效做法是给 agent 手和眼：用 skill 把应用拉起来，再用 CDP、模拟器或 API harness 去点、去看。一份从用户视角写的 feature map（路径、快捷键、选择器、预期结果）可以同时当指南和评分标准。

Property test 盯的是人容易漏、agent 也常在上面翻车的边界。先写下你认为不该破的命题，再用 fast-check、Hypothesis、proptest 这类库生成大量输入去证伪。常见命题包括往返编解码、账户余额不能为负这类不变量、迁移或重试的幂等，以及优化实现与朴素正确实现等价。对改写尤其有用：规格已经和线上行为脱节时，这些约束比过时文档更可靠。

Differential test 适合大规模迁移：同一批输入分别跑旧系统和新系统，结果不一致就说明有 bug 或破坏性变更。输入要用随机生成或生产流量抽样，并去掉空白这类无关差异；如果新环境本来就该和旧的不同，就把这些差异写成一份已批准清单。

## 验证首先是把改动跑起来

跑通整个应用，比堆测试更重要。网页改动可以用 Chrome 扩展，移动端用 iOS 或 Android MCP，桌面用 computer use，后端就把服务在本地拉起来。把启动模拟器或跑应用的步骤写成名叫 `verify` 的 skill，放进仓库里离相关代码最近的 `.claude/skills/`，需要几份就放几份。Claude 在提交前会去用这份 skill。它就是冒烟测试的 harness，值得先让它又快又稳。

失败的检查要引人。Claude 会跑检查并尝试修复；连续三轮还失败，就停下来找人。Code owner 写自己那一块的检查，并改到能抓住自己会抓住的问题；把人拉进来时，检查应直接说明原因，而不是让人从 diff 里猜。

他们还有一份 39 条的可靠性清单，每条都带一个能从 diff 里读出来的触发条件、对应检查，以及背后的事故或 PR。例如「`--resume` 能加载旧 transcript」：会话存储或消息类型一变，就要问新字段能否安全加载，因为旧 transcript 里没有这个字段。Claude 读 diff，只跑触发命中的那几条，通常是 3 到 10 条，不必把过去的故障记在脑子里。

审查不要靠叠更贵的第二位审查者，而要调好第一位。`REVIEW.md` 写清这块代码该盯什么。后面的轮次应接上前面的上下文和既有失败，而不是从头再扫一遍。

## 检查必须待在这次改动够不着的地方

如果一次改动能修改评判自己的检查，这套检查就已经坏了。Code Review 读的是 base 或默认分支上的 `REVIEW.md`，不是 PR 里改过的那份。闸门所在的规则，要放在这次改动改不到的分支上。

审查还要绑在具体 commit 上。审查进行时如果还有人在推，结论就过时了；一次通过如果落在已经过期的 commit 上，等于没审。便宜的检查要先跑：测试、构建、lint 在开 PR 之前本地完成。可以用 hook 在 Claude 结束时跑测试，或把通过测试套件写成 `/goal`。否则 agent 一推，占用的就是共享的审查和 CI 时间。

他们给每次提交打上验证方式的戳，也包括 `none`，这样才能查出哪些提交根本没被验证。另有一道提交闸门，会话里如果没有 `/code-review` 或 `/verify`，可以拦住提交。闸门有 off、observe、enforce 三档。新闸门先从 observe 开：只记录本来会拦住的提交，用来看误报、避免一上线就挡人。enforce 才会真拦。提交说明里可以写这次为什么没做验证；同一会话里若已经被拦过两次，下一次会放行，避免 Claude 卡死。

检查本身也要被检查。他们会看多少合入被 revert、维护者在合并前拒绝了多少，以及一份规模相当、之后一直干净的对照样本。Code Review 那篇还写过基于事故和 revert 的正式评估：把仓库回到当时的状态，只给一句话的标准答案，只有正确描述那个 bug 的发现才得分，并用已稳定合入的改动当对照，防止过分报。召回要分别看原始发现、验证之后、最终审查，避免三个阶段揉成一个端到端分数，把已经找到又弄丢的 bug 盖住。发现还要标重要程度：Important、Nit 或 Pre-existing，既有问题不算在这次作者头上。召回率调到再往上就会过拟合评估集、而不是真的多抓住 bug 为止。

漏掉的问题要写成规则。一种做法是从人工审查意见和 revert 里抽模式：至少在两个 PR 里出现过、并且能从 diff 里认出来，才有资格成为候选规则；再让三个 agent 尝试证伪，最后由人在 PR 里批准。另一种是拿三个找 bug 的 agent 回放已知事故对应的 PR：至少两个找到，说明这个 bug 可被检出；若是小 diff 仍然漏掉，就值得写进 `REVIEW.md`。Flaky 测试同样不能糊弄：不许跳过、加 sleep，或重试到通过。找不到根因，就删掉这条测试并写明原因。测试套件、验证步骤和 `.md` 只会越积越多，要定期清理。

## 可立刻落到本地编码 agent 的五点

1. 把启动应用、点主路径、看结果的步骤写成 `verify` skill，放在离代码近的 `.claude/skills/` 里，提交前先跑。先把它做快、做稳，再谈并行开更多 agent。
2. 测试优先投 E2E，再用 property test 锁住不该破的命题，迁移则加 differential test。Flaky 和过慢的测试会反过来教坏 agent，不要靠重试或 sleep 混过去。
3. 评判一次改动的规则（`REVIEW.md`、闸门、评估集）必须读自 base 分支，不能让这次 diff 改自己的检查。审查绑在具体 commit 上，过期的通过不算。
4. 新闸门先走 observe，记下本来会拦住的提交并打上验证戳（包括 `none`），误报看清楚再切 enforce。连续失败三轮，或闸门反复拦住，要引人，而不是让 agent 自己空转。
5. 把漏报、revert 和重复出现的审查意见收成规则，但要先经得起证伪和人审；规则和测试套件要定期删减，避免只增不减。
