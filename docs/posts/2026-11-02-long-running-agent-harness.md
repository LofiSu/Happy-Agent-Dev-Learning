这类 agent 的难点不在模型聪不聪明，在于它按班次干活：每个新会话都像换班的工程师，对上一班做了什么一无所知。上下文有限，中大型任务又不可能一个窗口做完，所以必须有个东西把会话缝起来。

Anthropic 的工程团队把自己踩过的坑写成了两条反模式和一个两段式解法。反模式一是想一次做完：整个 app 一口气塞进去，改到一半上下文耗尽，下一个会话接手时功能做了一半、还没记录，只能靠猜，时间全花在让基础功能重新跑起来上。反模式二出现在后期：已经有几个功能做出来了，新来的 agent 转一圈看到「有进展」，直接宣布完工。

## 初始化 agent 和编码 agent 分开

第一次会话用专门的提示词，只做一件事：把环境铺好。产物是三样东西——一个 `init.sh`（怎么起开发服务器）、一个 `claude-progress.txt`（谁做过什么）、第一个 git commit（哪些文件是新增的）。

之后每个会话只要求两件事：做一点增量，走之前留下结构化记录。文章里特别说明，这两个「agent」其实是同一个 harness、同一套工具，只是初始提示词不同。

## 功能清单是防「宣布完工」的那根钉子

初始化 agent 把用户那句高层需求展开成完整的功能清单。claude.ai 那个例子里是 200 多条，每条都是一句端到端的用户行为，初始全部标 `passes: false`。

编码 agent 只准改 `passes` 字段，别的不能碰。措辞也写得很硬：「删掉或修改测试是不可接受的，这会导致功能缺失或有 bug。」

格式用 JSON 而不是 Markdown，是个值得抄的细节：实验下来，模型更不容易乱改 JSON。

## 一次一条，收尾必须干净

「干净」的定义很具体：可以直接合进 main。没有明显 bug，代码有序、有文档，下一个人不用先收拾残局再开工。

做法就是每次结束提交 git，写一段进度总结。顺带的好处是模型能用 git 回滚坏改动，找回能跑的状态。

## 测试要像人一样做

还有一种失败：改完、跑了单测、用 curl 打过接口，就认定功能好了，其实端到端不通。

给了浏览器自动化之后，让它像用户一样点一遍，效果提升明显——很多读代码看不出来的 bug 才被抓住。当然有盲区，比如浏览器原生 alert 弹窗 Puppeteer 看不到，依赖弹窗的功能就更容易出问题。

## 每次开场只做五件事

`pwd` → 读进度文件 → 读功能清单 → `git log` → 跑 `init.sh`。先冒烟测一遍基本功能，坏了先修，别急着做新功能。

这套流程本身也省钱：不用每个会话重新摸索一遍服务怎么起、怎么测。

## 回到自己的 harness

骨架其实很小：一份能读的进度日志、一份不会被随手改歪的功能清单、一条快速回到工作状态的路径。三样东西都在上下文之外。

compaction 解决的是「一个会话内不爆」，这套解决的是「会话之间接得上」，是两条腿，缺一条都跑不远。

文章末尾承认没解决的问题也很实在：是该用单个通用编码 agent，还是拆成测试 agent、QA agent、清理 agent 这类专职角色，目前没有定论。
