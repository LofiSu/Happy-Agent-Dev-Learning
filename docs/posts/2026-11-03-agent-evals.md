评测最容易走两个极端。一个是觉得这事靠手感，靠手点和直觉顶着；另一个是一上来就想搭几百条任务的大套件，还没开始就把自己劝退了。

Anthropic 这篇给了一个低得多的起点：20 到 50 条从真实失败里抽出来的简单任务，就够开工。

## 先把词对齐

一条 task 是一次有明确输入和成功标准的测试。跑一次叫一次 trial——模型输出有随机性，所以要跑多次。grader 是打分逻辑，一条 task 可以挂多个。transcript 是整条轨迹，包含工具调用、推理、中间结果。outcome 是环境里的最终状态。

outcome 和 transcript 经常被混为一谈。订票 agent 最后说「已为您预订」，那是 transcript；数据库里到底有没有这条记录，才是 outcome。

还有两个容易混的名字：eval harness 是跑评测的那套基础设施，agent harness 是让模型能当 agent 干活的脚手架。评「一个 agent」，评的其实是 harness 和模型合起来的水平。

## 三类 grader

代码类：精确匹配、fail-to-pass 的二进制测试、静态分析、状态断言、工具调用校验。快、便宜、可复现、好排查，但碰上合法变体就脆。

模型类：按 rubric 打分、自然语言断言、成对比较、多评委投票。能处理开放式任务，但结果不稳定、更贵，必须和人工判定校准过才可信。

人：专家评审、众包、抽检、A/B。是金标准，用于校准模型 grader，但慢且贵。

常见组合是先让确定性的守住正确性，再让模型看质量，人只在需要时抽查。

## 能力评测和回归评测要分开

能力评测负责爬坡：起点通过率就该低，测的是模型还不会的东西。回归评测负责守成：通过率应接近 100%，掉分就说明有东西坏了。

能力评测爬到接近满分之后，可以毕业成回归集，从「还能不能做到」变成「还稳不稳」。

## 别用单次结果糊弄非确定性

`pass@k`：k 次尝试里至少成功一次的概率，k 越大越高。适合「只要有一次能成就行」的场景。

`pass^k`：k 次全部成功的概率，k 越大越低。用户天天要用的产品得看这个。

两者在 k=1 时相等；到 k=10，一个趋近 100%，一个趋近 0%。

## 八条能直接照做的

一，早开始，别等凑够几百条。二，从你现在手工检查的步骤和用户报的 bug 里收任务。三，任务不能有歧义：两个领域专家独立看，要能给出同一个通过或不通过的判断；写不出参考解，说明任务还没定义好。四，正反两面都要测，只测「该搜索的时候搜索」，最后会得到一个什么都搜的 agent。五，环境要干净、要隔离，他们内部就见过模型靠翻上一轮留下的 git 历史占便宜。六，grader 要看产物，不要盯路径，硬性规定工具调用顺序会把合法解法判死。七，该给部分分就给，能定位问题但没退款，比一上来就失败强得多。八，读 transcript，分数不涨的时候要能确认是 agent 的问题，不是评测的问题。

## 一个值得记住的数字

CORE-Bench 上，Opus 4.5 最初只有 42%。查下去发现三类问题：判分太死（期望 96.124991…，模型写 96.12 就算错）、任务描述模糊、随机任务根本没法精确复现。修掉判分 bug、换成没那么死的 scaffold 之后，分数到 95%。

所以 0% 通过率通常先怀疑任务坏了，而不是模型不行。

## 评测也不包治百病

自动评测、线上监控、A/B、用户反馈、人工读 transcript、系统的真人研究，各管一段。像安全工程里的瑞士奶酪模型：每一层都会漏，叠起来才够用。自动评测擅长发版前和 CI 里跑；线上监控负责接住真实流量里的意外；人读 transcript 负责校准「什么叫好」。
