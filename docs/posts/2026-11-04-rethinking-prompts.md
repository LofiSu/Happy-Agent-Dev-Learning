过去一年，给 agent 攒下的说明越摞越厚：skills、AGENTS.md、任务提示词。每换一版模型都值得回头看一遍这些说明，但模型能力跳一档的时候，这件事就从「值得做」变成「必须做」。

OpenAI 这篇专门讲为什么：以前为了把弱模型推回正轨加的脚手架，现在会变成负担。

## skill 的 description 越长，越容易被截断

每个 skill 的 name 和 description 都会进上下文，模型靠它决定要不要加载。description 写太长有两个后果：一是 skill 一多，宿主会帮忙截断，模型看到的部分更少；二是描述之间容易互相矛盾，或者过度强调「什么时候该用我」，结果该用的地方没用上，不该用的地方乱加载。

判断标准是短，同时把边界说清楚。反例大意是：写 Postgres 迁移，用于数据库、查询、模型或持久化相关的工作——这句话会让模型碰任何数据库相关的东西都来一下。正例把范围收到「新增或修改一条 migration，或评审它的上线」。

## 根文档当路由，不要当手册

读一个 skill 就占一份上下文，越读越接近 compaction，还把当前任务用不上的规则一起塞进来。

工作流不止一条的 skill，根文档应该是个最小的路由表，指到子文档和脚本。模型知道该去哪儿看就够了，不用逼它当场读完。

## 别再把 skill 写成分步菜谱

以前模型处理不了模糊性，把步骤钉死是帮忙。现在这些写得过细的说明反而拖后腿。

## AGENTS.md 要定期删

它对每个任务都生效，所以要逐条问：这条还需要吗。

「每次改之前先读 architecture.md、database.md、deployment.md」这类要求，改个错别字也要读三份文档，纯粹烧上下文。改成按场景引用：服务边界看 architecture.md，改 schema 看 database.md，准备上线再看 deployment.md。

还有个反直觉的点：老模型需要被推着去跑测试，新模型自己会跑。留着「改完必须跑全量测试」的老规矩，换来的是一堆多余的测试。

## 边界的话，别按最差的模型写

因为以前被不听话的模型坑过，所以写了很多「必须先问我」。对新模型来说，这些话会被认真执行，该继续的时候反而停下来。

重写的时候要问的是：这条边界现在还有必要吗，而不是当年哪个模型越界了。

## 把「完成」写在任务里

新模型有个反方向的毛病：更谨慎，做完第一版就回来请示，其实活儿还没完。

解法不是催，是派活时把完成条件写清楚——能起、能看一眼结果、失败的修掉，这些都算任务的一部分。「做完第一版先停下来给我看」这种要求，会把模型往更早的停点拉。

## 我自己的取舍

这跟「在 AGENTS.md 顶部写 if/then 强制触发」不矛盾，重心不一样：规则写条件，不写流程；触发写窄，别写宽。

还有一点得记住：这篇的建议是绑在具体模型上的。换模型就该重测一遍，没有一劳永逸的最佳提示词。
