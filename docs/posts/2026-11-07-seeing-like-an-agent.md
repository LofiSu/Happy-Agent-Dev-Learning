搭 coding agent 最难的一块往往不是提示词，而是工具面：给一个万能 bash，还是五十个专用工具？Anthropic Claude Code 团队把答案写成了「像 agent 一样看」——工具要贴合模型当下的能力，并且随着能力变化回访旧假设。全文大约只保留二十来个工具，加新工具门槛很高。

对本地 harness / soft skill 实践来说，这篇最值的是三组失败实验：结构化提问怎么做成工具、Todo 如何变成 Task、以及用渐进披露代替再堆一个工具。

## 提问：别塞进别的工具，也别靠解析散文

他们想降低人和模型之间的问答摩擦（elicitation）。第一版最省事：给 ExitPlanTool 加一个 questions 数组，计划和问题一起交。结果模型懵了——答案和计划打架怎么办？要不要再调一次 ExitPlanTool？这条路立刻废掉。

第二版改输出格式：让模型用带选项的 Markdown 列表提问，再解析成 UI。模型「通常」能写对，但不稳：多写几句、漏选项、半路放弃结构。

第三版才做成独立的 AskUserQuestion：任意时刻可调，计划模式尤其鼓励；弹出模态、阻塞循环直到用户答完；还能在 Agent SDK 或 skills 里被引用。关键不是「我们觉得漂亮」，而是模型愿意调、调出来的结果也好用。最好的工具设计，也要先过「模型会不会用」这一关。

## 能力涨了，脚手架可能变成手铐

早期 Claude Code 需要 TodoWrite 把任务钉住，还每 5 轮塞系统提醒，防止忘事。模型变强之后，提醒反而绑死了它：明明该改道，却死守清单。子代理也难共享同一份 todo。

于是 Todo 换成 Task：可写依赖、跨子代理同步、可改可删。重点不是「待办 UI 升级」，而是工具是能力的函数——昨天帮你的约束，今天可能在挡路。支持的模型集合宜窄、能力剖面接近，否则工具表要分裂维护。

## 给找上下文的能力，别硬塞上下文

内部第一版用过 RAG：向量库预索引代码，每次响应前塞片段。快，但要索引、环境一变就脆；更关键的是，上下文是被塞给 Claude 的，不是它自己找的。

后来改 Grep 等搜索工具，让模型自己建上下文。Skills 把渐进披露形式化：主文件指向 references，按需再读。产品自述类知识（怎么加 MCP、slash 是什么）也不塞系统提示——那会 context rot、抢编码主业。做法是挂一个 Claude Code Guide 子代理：它在自己的上下文里搜文档，只把短答案交回主 agent。

原则很干脆：能用 skill / 子代理 / 文件树解决的，不要再加工具。工具是动作空间里的选项；选项一多，决策就差。

## 可立刻落到自己仓的四步

1. 列出现有工具表，标「上次有人真正依赖它是何时」；冷门专用工具先试 skill + bash 能否替掉。
2. 新能力先问三句：模型会不会调？调了是否更好？能否用 skill / 子代理代替？
3. 结构化人机问答做成工具，别靠解析自由文本；观测触发率，不调就重设计。
4. 模型升级时专门开一次工具审计：哪些提醒、哪些硬闸已经在约束新能力。
