OpenAI 11 月 19 日发了一篇工程文，讲他们怎么用 Codex 在云里自动查找、修复并核对性能回退。系统名叫 Performance Factory：工程师定义会反复跑的工作流，再给各步骤写指令。告警一响，Regression Workflow 就开一条任务；agent 调查并记下发现、提出修复，等人审阅；部署之后，另一个 agent 再核对性能有没有回到基线。文里给出的数字是：三个多月里，这条工作流跟了 1700 多次调查，定位了 600 多件的根因，大约每天 17 次自动调查。

昨天那篇写的是本机跑命令时，permission profile 怎么卡住文件系统和网络。这篇换到生产侧：一次会话里的调查，怎么变成可以交接、可以挂起、可以恢复的任务。

## 从「把告警贴进 Codex」到一座工厂

他们把这条路写成六步。关键是工作方式一层层从人手里交出去。

Codex 出现之前，工程师自己看指标和日志、对比 trace、登机器、读代码。同类问题反复出现后，他们做了 CPU、分配分析一类工具，后来积累了 30 多种性能工具。有了 Codex 当搭档，工程师可以问「为什么变慢了」，让它在不熟悉的系统里搜代码、找指标和 trace，再顺着服务之间的调用把经过拼出来。但每一步仍要人来指路：该用哪套工具、下一步看什么。

再往后，他们把调查流程收进共享 skill `perf-forensics`：有哪些工具、何时用、怎么从几个角度走——回退从何时开始、影响哪些请求、部署或配置变更能不能解释。再用历史回退做 eval，改 skill。针对他们关注的那类问题（比如 ChatGPT 延迟和可用性下跌），可以把一条告警交给 Codex，单次 run 拿到诊断，不必逐步盯着。

skill 成熟之后，人反而成了告警和 Codex 之间的中转：把告警复制进去，再把结论贴回 Slack。下一步是把调查搬到云上，告警自动开 Codex 会话，结论直接回 Slack 线程。自动化到这里就停了：补丁还得人写，部署后还得人核对；告警一多，连哪些回退值得看，都要在 Slack 线程里翻。

Performance Factory 要做的，是把整段工作流跑起来。它跟踪每条进行中的任务下一步要什么，步骤就绪就派一个 agent。任务自己保存状态和发现，工作可以在 agent 和工程师之间交接，代码审查或部署之后也能接着干。对回退来说，起点是调查告警，终点是在生产里确认已经恢复。常见优化也可以写成定期跑的工作流；一条工作流发现可疑点，还能在另一条工作流里开任务，去验证和落地。

## 四件零件：任务、调度、云上的 Codex、订阅

任务服务是工程师写工作流的地方：配置文件加上给 agent 看的 Markdown 指令。配置列出任务可以经过的状态、允许的转移，以及哪些步骤必须由人来做；各步骤另有一份 prompt，说明这一步该干什么。文里举的是一次代码变更任务：`code-change/config.toml`，再加 `work/implementing.md` 和 `work/reviewing.md`。每件工作都是某条工作流里的一条任务，界面里都能看到，也可以拉上更了解情况的同事。

调度循环定期查看哪些任务已经可以进入下一步，按当前状态的指令启动一轮 Codex，让 agent 把进展写回任务，做完就把状态往前推。

任务派出去之后，agent 要能用上工程师常用的那套东西。他们做了内部 API，在云里程序化地拉起一轮 Codex：跑在公司网络内的环境里，能访问代码仓库，也能用指标、日志、trace、CPU profile 和内存快照。agent 以服务身份运行，权限可以收窄，也能分清哪些动作来自性能 agent。搬到云上之后，调查可以并行，不必等某台笔记本开着，也不用人手维护一台台云开发机。

有的步骤要等人审，或等一次部署，这段时间不必让 agent 一直挂着。任务可以订阅事件，比如 GitHub 上的审查评论、失败的 CI，或部署完成。事件匹配后，任务重新变为就绪，调度循环再派一个 agent 接着干。

## 回退工作流：发现写在任务上

第一条落地的工作流就是 Regression Workflow。一条性能回退会经过「需要调查、已找到根因、已提出修复、已解决」这几个阶段，自动化工作流按同样的阶段往前推。

配置好的性能告警一响，就开一条任务，由 agent 接力往下走。状态和关键发现写在任务上，不写在某一次 agent 的上下文里，换一个 agent 或工程师也能接着看。工程师可以在 Slack 或工作流界面里跟进、补充上下文、审提案。修复部署之后，agent 核对性能是否回到原先的基线，再决定要不要标成已解决。

查根因是第一段硬活。agent 先弄清哪些指标变差、从何时开始、影响了哪些服务请求。`perf-forensics` 给它工具和剧本。告警是指标越过阈值才响，回退可能几小时前就开始了，所以要先回头找指标最初变差的时间点。接着比较请求分组：是同类请求变慢了，还是慢请求本身变多了？这两种指向不同原因。时间范围清楚之后，再看部署和 feature flag，读相关代码，核对该变更何时真正打到受影响的请求，并用日志或 trace 验证代码能不能解释观察到的现象。

早期 agent 常常停在第一个说得通的解释上，有的后来证明是错的。他们加了一道对抗审查：另开一轮 Codex，专门试图推翻这份诊断，复核前提，并试反事实。如果认定是某次放量，没被放量的同类请求是否仍然健康？如果怀疑的变更被回滚，相关指标有没有恢复？文里举过一例：一次调查把失败的 ChatGPT 对话归到图片下载出错，并标成根因已找到；审查那一轮发现，负责定位文件的内部服务其实已经恢复，但图片请求还在失败。诊断解释不了仍在发生的失败，审查就把调查重新打开，并记下还缺什么证据。

他们把大活拆成更短、目标更清楚的 Codex 轮次。人工回看 100 条根因建议时，有 70% 被评为准确，其余 30% 还需要继续收紧，或没把因果关系说满。工作流里，调查、反驳诊断、提出修复由不同轮次分担，用互相制衡来提高准确率。

把修复做对，比找到原因更难。诊断通过对抗审查后，工作流让 Codex 写修复并开 PR，由工程师决定合不合。交接上他们花了不少力气：每条任务都有一份自动生成的报告，概括回退、影响、根因和提案，并带上指标时序、CPU flame graph 和 trace，方便人先扫结论、再核对证据。工程师可以直接改 PR，也可以只借用诊断自己写补丁。PR 上留下评论，工作流会叫醒一个 agent 去处理。

工程师部署之后，工作流再叫醒一个 agent，看性能有没有回到更早的基线。恢复了就标成已解决；只恢复一部分，就结束原来那条回退，并为剩下的变慢新开一条任务——剩下的部分可能是另一个原因；没有任何改善，就记下经过，把回退送回调查。他们也给提案加了对抗审查，检查补丁是否对准根因，并帮忙抓住附带问题。有些改动是架构取舍，比如加缓存可能让性能变好，也会让人读到旧数据，这类事更适合熟悉服务的人来权衡。他们还在拿 agent 的提案和工程师最终合入的改动对比，用来做 eval、改进工作流；并尝试在请人审之前，先用合成性能测试衡量提案、再改一版。

## 可立刻落到自己仓的五点

1. 调查不要只留在某一次会话或 Slack 线程里。任务要有明确状态，发现写在任务上，换一个 agent 或人也能接着干；审查或部署之后，靠事件把任务重新唤醒。
2. 先把调查流程收成 skill：有哪些工具、何时用、怎么走。用历史回退做 eval，单次 run 能稳定给出诊断，再考虑让告警自动开跑。
3. 第一轮说得通的根因，交给另一个独立会话去反驳；修补丁也一样。修复往往比查因更难，涉及缓存和一致性这类取舍时，仍要人来决定。
4. 等人审或等部署时，用订阅把任务挂起，事件到了再调度，不要让 agent 空转。agent 用服务身份运行，权限收窄，动作也查得到是谁做的。
5. 改 skill 或换模型前，用历史事故做回测；查因准不准，和交接摘要对人是否有用，要分开测。回测时不要让 agent 读到事后的事故复盘，或上次调查留下的笔记。工具故障和缺权限也要盯，同一错误反复卡住调查，就开任务修自己的工具链，合入后再用 eval 确认卡点已经过去。
