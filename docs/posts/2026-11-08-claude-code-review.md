Claude Code 团队说过，Claude 写了他们自己代码的大约九成。代码量涨起来之后，人逐行读完每一个 diff 几乎做不到。Anthropic 整个 monorepo 每天落地的变更，从五月大约 2500 条涨到九月超过 3 万条；Claude Code 虽然不在那个 monorepo 里，压力一样大。他们六月到九月合进 Claude Code 仓的 PR 翻了一倍多，需要 revert 的比例反而降了四成以上。

办法不是取消 review，而是换一个问题：别再问「有没有人读过这段代码」，改问「这件事可能怎么坏，该由哪一层检查抓住它」。Review 从末道闸变成写代码时持续跑的检查，大多数改动在人看之前，已经被 Claude 审过并修过至少一轮。

对本地编码 agent 实践来说，这篇最值得抄的不是「上一个自动审 PR 的 bot」，而是整条链路：PR 之前先自证、每层抓一类问题、按风险决定要不要人、并且让自动 review 收敛而不是通宵互撕。

## PR 之前就审完一轮

大多数 review 发生在 PR 出现之前。他们给 Claude 能跑的东西——测试、构建，或者一张能对照设计的截图——并且要求它出示输出，而不是口头说做完了。然后用一份干净上下文的子代理再读一遍 diff。Boris Cherny 的说法是：给 Claude 一条能自证对错的路径，大概是出好结果最重要的一件事，最终质量能差两到三倍。验证长什么样因领域而异：一条 bash、一套测试，或者在浏览器 / 模拟器里点一遍。

不少人还会在开 PR 前跑几个内部 skill：找 bug、精简 diff、端到端核对行为。UI 改动再对照设计规范走一遍。重复被自动审指出的问题，就回到源头修：写进 skill、加成 lint，或更新说明文件。

两份短文档很关键。`CLAUDE.md` 告诉模型这个项目是什么：技术栈、约定、目标和非目标。每次 review 都会加载它，所以大仓里要写短，细节用链接指出去。`REVIEW.md` 由 code owner 写，告诉审的那一侧「这里失败长什么样」——文档仓是「它在撒谎」，配置仓是「它走错路」——并且限制 nit、列出该跳过的路径、要求指出文件和行号当证据，摘要以计数开头，没什么可修就直说。

## PR 上的自动审，要投票，也要收敛

每个 PR 在人看之前都会先过一轮 Claude review：对照整个仓库和 PR 自己声明的意图，问这次改动是否解决了问题、是否合进现有系统、会不会弄坏别的。公开产品 Code Review for Claude Code 已在 Team / Enterprise 上线，本地也可以跑较轻的 `/code-review`。研究预览阶段，内部有实质评论的 PR 占比从 16% 升到 54%；超过 1000 行的 PR 多半会有发现，小改动则多数是干净的。仓库可以设成 Quick、Standard 或 Deep，漏一个 bug 代价很大的地方才值得用 Deep。

发现不会直接甩给人。几组 agent 同时找 bug，另一组对每条发现投票，够票才发出来；只谈风格、诊断或清理的会被丢掉。留下的按严重程度标成 Important、Nit 或 Pre-existing，避免把原本就有的问题算到这次作者头上。每条发现都必须回应：修好，或者关掉并写原因。经常是另一个 agent 隔夜就把修复补上了。

安全审查是单独能拦合并的一层。bug review 或 security review 还有未关闭的发现时，PR 合不了；修掉，或者用一句话关掉误报。自动化检查（lint、类型、各平台测试、构建）同样是硬闸。PR 模板会问怎么测的、怎么回滚；Claude 可以代填，但发起改动的人要签字。

自动审有个容易被忽略的陷阱：作者如果也是 agent，一条 nit 它会当真去改，于是又一次提交、又一轮 review。他们有过一个 CLI PR 隔夜来回修了五十多轮。用 git blame 看持续被指出的代码，大约 59% 在第一轮就已经在那儿了——后续轮次很少发现新 bug，只是每次多挖一点旧的。

于是他们改了复审规则：三轮之后请作者退后看方案，而不是继续打补丁；前几轮之后只审新增 diff；按「这一类 bug」而不是某一行来报；已经发过的发现不再重复。他们同时跟踪 rounds-to-pass，并把事故和 revert 收成每日跑的 eval 集。优先级写得很清楚：先抓住真 bug，再减少轮次。

## 人审按风险分级，机器人的批准不算人数

不同改动风险差很多，所以人审的份数也不一样。文档、文案、仅内部功能、放在 flag 后面的加法，自动审和安全检查绿了可以不再等人。普通产品改动，以及缓存、自动更新、系统提示这类敏感区，要一个人。最高风险的代码，再加上一小批路径，要两个人。

分级看的是这次改动，不是谁写的。一个分类器先定风险档，另一个再问「这一次是否仍要多一个人」。敏感路径和任何 CI workflow 文件永远要人看。更轻的合并路径只给仓库信任名单上的作者；其他人即使改动档位低，也要第二个人批。Agent 的批准永远不能顶替一个人。谁指挥 agent 写的，谁就算其中一个必需的审查者，跟自己手打代码一样。批准绑在具体 commit 上，来了系统无法担保的新提交（比如 agent 再推一版，或有人手解消了冲突），就要重新批。

人仍然要做自动检查做不到的事：这东西该不该做、架构会不会被别人抄走、证据（测试输出、跑过的命令、截图、自动审的发现）是否足以让你说得出「这些检查会漏什么」。说不出来，就该认真审，而不是随手点通过。每条合进去的改动都有人对结果负责。他们的团队习惯是「你落地，你兜着」：改动保持小、可回滚、用 flag 和分阶段发布把爆炸半径收住；出事不是为了问责，而是因为你上下文最多。

共享对代码的理解，也不再靠人把每个琐碎 diff 读一遍。需要摸某一块时，让 Claude 按当前代码写一份切片说明，比读一行文案改动学到的多得多。

## 可立刻落到自己仓的四步

1. 给 agent 一条能自证的路径（测试、构建或可对照的截图），开 PR 前用干净上下文的子代理再读一遍 diff；反复出现的评论写进 `REVIEW.md` 或 lint，不要每次口头说。
2. 给 PR 模板加上「怎么测的 / 风险 / 怎么回滚」，并要求每条自动审评论必须关闭才能合并。
3. 按改动而不是按作者写清风险档：低风险可以只走自动检查，敏感路径和 CI/发布相关文件必须有人；机器人的批准不计人数。
4. 给自动 review 加上收敛规则：轮次上限、之后只审新 diff、按类报 bug、不要重复已发过的发现。把事故和 revert 收成回归集，改审查提示或模型时重跑一遍。
